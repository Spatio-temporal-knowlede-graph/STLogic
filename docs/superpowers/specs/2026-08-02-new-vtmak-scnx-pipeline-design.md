# new_VTMAK — 시나리오 원문 → VR-Forces `.scnx` 파이프라인 설계

작성일: 2026-08-02
대상 디렉터리: `new_VTMAK/`
선행 프로젝트: `VTMAK/` (백마고지 시나리오, 14일차 캠페인)

---

## 1. 목적

`new_VTMAK/scenario_original/scenario_v3.txt` 하나를 입력받아 VR-Forces 4.9
`.scnx` 시나리오 파일을 결정적으로 자동 생성한다. 생성된 시나리오를 VR-Forces
에서 실행하고 Data Logger로 수집해 시공간 지식그래프(STKG) 데이터셋을 만든다.

최종 목표는 선행 프로젝트 `VTMAK/`와 동일하다. 시나리오와 지형 좌표 체계가
바뀌었고, 그 과정에서 선행 프로젝트가 스스로 기록한 한계 세 가지를 해소한다.

## 3. 좌표 엔진

> **2026-08-03 갱신 — 이 절의 결론은 대체되었다.** 사용자가 golden
> `yewon_test.oob`에 새 시나리오의 지명 통제점 23개를 직접 찍었다. 3.1의 전제
> (golden에 새 지명이 없다)가 무너졌으므로, 좌표는 로컬 미터 선언이 아니라
> **golden 지형점 앵커링**으로 돌아갔다. `scale`·구역별 레이아웃·해안선 모델은
> 제거했고, 원문에만 있는 지명 6곳만 `config/layout_rules.json`의 규칙으로
> 파생시킨다. 3.2~3.6은 그 경위의 기록으로 남긴다. 현재 동작은 `new_VTMAK/README.md`
> "좌표" 절을 볼 것.

### 3.1 문제

golden `yewon_test`에는 이름 붙은 지형점이 9개 있으나 전부 **선행 시나리오의
지명**(백마고지 정상, 화랑고지 전초, 284고지 관측소 등)이고, 새 시나리오의
지명 27개와는 두 개만 겹친다. 게다가 9점 전체가 **남북 1.81 km × 동서 1.02 km**
안에 몰려 있다.

원문에는 거리 수치가 전혀 없다(전부 "남측/북측/중앙/서측/동측" 정성 표현).

### 3.2 핵심 발견 — 단일 전역 스케일로는 불가능하다

시나리오의 교전 제약이 두 종류이고, 서로 반대 방향의 축척을 요구한다.

| 제약 | 교전 쌍 | 요구 |
|---|---|---|
| 직접사격 | 중앙 킬존 남측 → 중앙 킬존 (M4 → AK47/T-72/M1A2/BTR-60) | ≤ 500 m |
| 직접사격 | 중앙 계곡 북측 → 남측 제1방어선 전방 (AK47 → M4/T-69) | ≤ 400 m |
| 간접사격 | 아군 포병진지 → 적 포병·박격포진지, 적 북측 접근로, 중앙 킬존 | ≥ 2,000 m |
| 간접사격 | 적 포병진지 → 남측 제1방어선, 아군 포병·박격포진지, 중앙 킬존 | ≥ 2,000 m |
| 간접사격 | 박격포진지 상호 (MO-120RT-61) | 1,100 ~ 8,100 m |

`map_pack.json`에 배율 하나를 곱하는 선행 방식으로는 둘을 동시에 만족시킬 수
없다. 포병에 맞추면 소총 교전이 사거리를 넘어 죽고, 소총에 맞추면 포병이 최소
사거리 미달로 스킵된다. 선행 프로젝트의 "1.85배 하드코딩"과 "사거리 미달
간접사격 자동 스킵"이 이 충돌의 흔적이다.

### 3.3 해법 — 구역별 레이아웃

시나리오 구조가 해법을 허용한다. 빡빡한 교전은 전부 중앙에 몰려 있고 포병은
전부 후방에 있다. **중앙을 조밀하게, 종심을 넓게** 두면 두 제약이 동시에
성립한다.

`config/battlefield_layout.json`에 로컬 미터 좌표계(북 = +y, 동 = +x)로 선언한다.

```jsonc
{
  "origin": { "lat": 21.3860, "lon": -157.7420 },  // yewon_test 지형점 중심
  "bearing_deg": 0,
  "scale": 1.0,
  "locations": { "LOC_중앙킬존": { "x": 0, "y": 0, "radius": 200 }, ... }
}
```

### 3.6 투영

로컬 미터 → WGS84는 origin 기준 등거리 근사
(1° lat = 110,574 m, 1° lon = 111,320·cos φ). 7 km 범위에서 오차 1 m 미만.
그 다음은 선행 프로젝트와 동일하게 WGS84 → ECEF geocentric 미터로 변환해
`.oob`에 기록한다.

고도는 0으로 두고 VR-Forces의 **Ground Clamping**에 맡긴다(로드 시 켜기 필수,
Cutoff Distance Scale 최대).

`scale`·`origin`·`bearing_deg`가 전부 config 값이므로 선행 프로젝트 한계 1번
(스케일 하드코딩)이 구조적으로 해소된다.

## 4. 파서와 이벤트 모델

### 4.1 방식 — 결정적 템플릿 매칭

원문은 기계 생성 텍스트이고 문장 템플릿이 유한하다. 프로토타입으로 검증했다.

- 3,000문장 중 **2,999 매칭, 미매칭 1건**
- 미매칭 1건은 원문 마지막 줄의 절단 조각(`**M1028 `)이다. 원문 PDF 자체가 여기서
  끊겨 있으며 변환 손실이 아니다. 파서는 이 조각을 **선언된 예외**로 처리하고
  리포트에 명시한다. 조용히 버리지 않는다.
- 추출 결과: 지명 27, 이동 행동 7, 상태 18

객체 ID가 문장에 명시된다(`**US Army M4(FR-INF-001, 방어 보병 1)**`). 따라서
행위자·대상 판정이 추측이 아니다. 선행 프로젝트가 겪은 "행위자와 대상이 뒤바뀜"
(커밋 26fa796) 류의 문제는 원인 자체가 사라진다.

### 4.4 이벤트 술어

STKG 술어 19종을 채택한다. 이는 원문 저자가 정의한 downstream 스키마이며,

`locatedAt, moveTo, gatherAt, approach, aimAt, fireAt, indirectFireAt,
directFireAt, supportFireAt, hitArea, hitBy, damagedBy, suppressedBy,

### 4.5 플랜 보강 제거

선행 프로젝트는 이벤트가 없는 객체에 백마고지 탈환 기본행동을 `spec.py` 코드
상수(`_OBJECTIVES`, `_ENEMY_TARGETS`)로 주입해 태스크 커버리지를 49% → 98%로
올렸다. 새 시나리오는 필요 없다 — **task 가능 328객체 중 이동·사격 행동이 없는
객체가 0개**임을 확인했다. 해당 상수를 제거한다. 선행 한계 3번 해소.

## 5. `.scnx` 저작

### 5.1 golden 교체

`ys2 (1).scnx` → `yewon_test`. 용도가 둘로 나뉜다.

- **좌표 수확: 사용하지 않는다.** `battlefield_layout.json`이 대체한다.
  `harvest_golden.py --only coords`에 해당하는 경로를 폐기한다.
- **엔티티 레코드 템플릿 + boilerplate: 사용한다.** DIS가 정확히 일치하는 golden
  실레코드를 복제해야 로드·실행이 안전하다는 선행 발견은 유효하다.

### 5.2 golden 모델 커버리지 (해소됨)

초기 대조에서 `yewon_test` zoo에 3종이 없었다(M1A2 Abrams, MIM-104 Patriot,
Russian Soldier SA7 — 영향 21객체). 2026-08-02 golden이 갱신되어 전부 들어왔다.

| golden marking | DIS | 대응 모델 |
|---|---|---|
| `M1A2 1` | `1 1 225 1 1 3 0` | M1A2 Abrams MBT |
| `SAM 3` | `1 1 225 28 2 0 0` | MIM-104 Patriot Launcher |
| `R 1` | `3 1 222 11 45 1 8` | Russian Soldier SA7 |

`yewon_test.oob` 744,862 → 854,990 바이트, 객체 43 → 46.

**시나리오 필요 모델 26종 전부가 `dis_catalog.csv` 항목과 golden 레코드를 동시에
갖췄다.** 레코드 복제는 marking이 아니라 DIS 7튜플로 매칭하므로 golden의 marking이
모델명과 달라도 무방하다. 선행 프로젝트가 "종류별 대표 복제"로 우회했다가 모델
불일치 hang을 겪은 문제는 발생하지 않는다.

이 매칭이 유지되는지는 G3가 검사한다 — 스펙의 모든 `entity_class`가 golden에서
DIS 완전일치 레코드를 찾지 못하면 FAIL.

### 5.3 정적 객체 7개 — 좌표로 처리

간접사격의 목표로만 등장하는 객체 7개는 엔티티로 만들지 않는다. 역할 텍스트가
타임라인에 명시되어 있어 지명 바인딩이 원문에서 직접 나온다.

| ID | 원문 역할 | 바인딩 지명 |
|---|---|---|
| `FR-FP-001` | 아군 자주포 사격진지 | 아군 포병진지 |
| `FR-FP-002` | 아군 박격포 사격진지 | 아군 박격포진지 |
| `FR-LN-001` | 아군 제1방어선 | 남측 제1방어선 |
| `EN-FP-001` | 적 자주포 사격진지 | 적 포병진지 |
| `EN-FP-002` | 적 박격포 사격진지 | 적 박격포진지 |
| `EN-RT-001` | 적 북측 접근로 | 적 북측 접근로 |
| `OBJ-009` | 중앙 킬존 | 중앙 킬존 |

사격은 `task_catalog`의 `ffe-on-location` 템플릿(좌표 대상 간접사격)으로 저작한다.

**받아들이는 대가**: 이 7개는 시뮬레이션 안에 실체가 없으므로 Data Logger에
기록되지 않는다. 원문의 "피격 지역 상태로 전환한다" 21건은 `build/events`
JSONL에만 남고 Data Logger 출력에는 나타나지 않는다. STKG 구축 시 두 소스를
합쳐야 한다.

### 5.4 유지하는 것

선행 프로젝트에서 실측으로 검증된 자산이므로 손대지 않는다.

- 좌표계 ECEF geocentric 미터, 참조 표기 `"VRF_UUID:<uuid>"`
- 결정적 UUID(uuid5)로 파일 간 ID 일관성
- marking ASCII화 (한글 marking이 DIS 11 byte 한계를 넘겨 깨지고 클릭 불가해지는 문제)
- `.omp` 재생성 (golden uuid 참조 시 객체가 안 뜨는 문제)
- jitter ±25 m (같은 지점 공유 객체 겹침 방지)
- `.scn` / `.oob` / `.pln` / `.omp` 저작 + ZIP 패키징

## 8. 가정과 위험

1. **Ala Moana 지형이 6.8 km × 4.0 km를 커버하는지 확인되지 않았다.**
   이 PC에 VR-Forces가 설치되어 있지 않고, golden에 담긴 것은 지형 자체가 아니라
   그 위의 점 9개뿐이다(그 9점은 1.8 km × 1.0 km에 몰려 있다). 대응: `scale`이
   config 값이므로 로드 후 조정 가능하며, 0.71 미만으로 줄이면 M109 최소사거리가
   깨져 G0가 잡는다(§3.5).

2. **고지·능선의 의미가 지형에 없다.** 중앙 고지·서측/동측 능선·남측 고지
   관측소는 이름상 고지지만 실제 그 좌표가 평지일 수 있다. Ground Clamping이
   붙여주긴 하나 표고 차는 보장되지 않는다. 필요 시 지형 고도 프로브로 고지점을
   찾아 스냅하는 옵션을 추후 추가한다.

3. **M901 / MIM-104 Patriot의 간접사격.** 원문은 이들을 "로켓화력 대체 객체"로
   두고 지상 간접사격을 시킨다. VR-Forces에서 Patriot은 SAM 발사대라 지상
   `ffe-on-*` 태스크가 성립하지 않을 수 있다. 선행 프로젝트에서도 M901 4객체가
   무기체계 미확정으로 태스크 없이 남았다(선행 한계 6번). 대응: `weapon_ranges.csv`
   와 `task_catalog`에서 이 두 모델을 별도 처리하고, 태스크 생성 불가 시 G0/G2가
   **명시적으로 보고**한다.

4. **정적 객체 7개가 Data Logger에 안 남는다** (§5.3). 의도된 선택이며 STKG
   구축 시 이벤트 JSONL과 합쳐야 한다.

5. **원문 마지막 줄이 절단되어 있다.** FR-TRK1-003의 종료 상태 문장 하나가
   유실. 원문 자체의 문제이며 파서가 예외로 선언 처리한다.

6. **고도는 Ground Clamping 의존이므로 Data Logger의 고도값은 근사다**
   (선행 한계 5번, 그대로 유지).
